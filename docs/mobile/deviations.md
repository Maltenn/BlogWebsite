# The deviation register

Every place where an app is NOT the site: what differs, which platform forced it, and why. The apps ship `public/app.css`
and every page module byte for byte, so **the web view's pixels are the site's pixels**. What is listed here is either
outside the web view (native bars, splash, system sheets), inside it only through a `<meta>` tag or script behaviour, or a
property of the platform that the pixel diff will show.

Two rules: a row is added in the same change as the thing it records, and a row with no reason does not count. Nothing in the
register is a change to `app.css`. If one ever has to be, it gets a row first (see contract.md §11).

Status: **in force** (the app does this today), **not built** (the row records a thing deliberately left as the web has it),
**placeholder** (nobody has the real value yet), **unverified** (written, never run on a device; the instrument that would
verify it is named).

## Appearance

| D1 | A solid **#1c3f94** band behind the status bar. The page is laid out below it, not drawn under it. | iOS, Android | `app.css` has no `env(safe-area-inset-*)` and must not gain one. The only way to keep the header off the notch with the CSS untouched is to give the web view a frame inside the safe area. #1c3f94 is the first row of `.ms-header`'s gradient, so the band meets the header with no edge. | iOS `ShellViewController` (`SceneDelegate.swift`); Android `MainActivity.paintBands()` | in force, unverified (plates on a notched device: checklist 23) |
| D2 | A solid **#eef4ff** band behind the home indicator / gesture bar. | iOS, Android | Same reason. #eef4ff is `.os-foot`'s colour, so the band reads as the page's footer. When the page is not scrolled to the end it is a plain strip under the content. | same | in force, unverified |
| D3 | **The tab bar is native, and the web `.ms-tabs` is taken out of the page.** The bar is drawn by the shell, pinned along the bottom of the window, above the home-indicator / gesture band. The page's own `.ms-tabs` is moved out of the flow (one inline style; `app.css` is untouched) and the 28px it occupied under the header is given back to the page. | iOS, Android | Guideline 4.2: with no native interface, the first thing a reviewer touches is a row of 12px web buttons in a WebView. **Why it is matched rather than approximated**, which is what the first version of this row said could not be done: nothing about the bar is written down in Swift or Java. `public/js/core/tabspec.js` MEASURES the live `.ms-tabs` — every rectangle, colour, font, string and baseline — in the web view that is running, and the shell draws exactly that. | D22 | **Where the tab bar is.** The site puts `.ms-tabs` in the page, under the header, where it scrolls away; the app pins it to the bottom of the window. The web view is laid out ABOVE it, so the page's viewport really is shorter and the site's own bottom furniture (`.ms-fab`, `.ms-resumebar`, `#toasts`) sits on top of the bar, not behind it. The cost is real and is this row: a page scrolled to the top no longer has the blue strip under its header. | `SceneDelegate.swift`, `MainActivity.java` | in force, unverified on a device |

Scrolling to the active item is what every native tab strip does and the one place this bar is deliberately *better* than the web one rather than equal to it — which is why it is a row here and not a silent improvement. | `TabBar.swift`, `TabBar.java` | in force, unverified |
| D4 | The page renders in the phone's fallback font, not Tahoma. `app.css` asks for `'MS Sans Serif', Tahoma, 'Segoe UI', Arial`; iOS resolves that to Arial, Android to its system sans (Roboto on Pixel and most others, Samsung One on Samsung). | iOS, Android | It is what the same CSS does in a phone's own browser. Recorded so the pixel diff's reference plates are captured with the same fallback, not on a machine that has Tahoma. | none | in force (a property, not a change) |
| D5 | On iOS the viewport meta gets `, maximum-scale=1` at start-up so that focusing a field does not zoom the page. Pinch zoom still works. | iOS | The site's fields are 11-12px; WKWebView zooms any field under 16px on focus, and the fix without touching `app.css` is the viewport. This is the one change to the page's `<head>`, made by `native.js`, never by `index.html`. | `native.js` | in force, unverified |
| D6 | Position-fixed elements at the bottom (`.ms-fab`, `.ms-resumebar`, `#toasts`) sit **above** the keyboard. | iOS, Android | The web view is resized for the keyboard (`keyboardLayoutGuide` on iOS, Capacitor SystemBars' IME padding on Android) so a focused composer is never covered (checklist 24). ## Behaviour a person will notice

| # | What differs | Platform | Why | Status |
|---|---|---|---|---|
| D12 | The file chooser for a picture is the phone's own sheet ("take a photo", "choose from my photos"), not the web view's. The page's own `<input type="file">` and its upload code are untouched; the picked file is put into the input. | iOS, Android | The native picker and camera are a Guideline 4.2 item and a better picker; falls back to the web chooser if the plugin refuses. | in force, unverified |
| D13 | "copy link" on a blog post opens the **share sheet** with the site's real address (`https://<origin>/...`), and anything the page copies that starts with the app's own origin is rewritten to the site's. | iOS, Android | In the app `location.href` is `capacitor://localhost/...`, which is nobody's address. | in force |
| D14 | Links that leave the site, and members' photos opened as a link, open in the system browser (Safari View Controller / Custom Tab), never inside the web view. | iOS, Android | A page that navigates the app's web view away from the bundle cannot get back. | in force |
| D15 | "Connect Google / Discord / Spotify" in Settings shows a message and does nothing; sign-in with Google or Discord from the login page works. | iOS, Android | `GET /api/oauth/:provider/start` refuses `client=app` for anything but a sign-in (`src/accounts/oauth.js`), because a system browser sheet has no session cookie to say who is linking. Needs a contract change (a one-time link ticket) before the app can do it. | not built (contract gap) |
| D24 | **The sign-up screen has a "use a photo of my own" button** above the fold, which opens the phone's camera / photo-library sheet. The site's sign-up offers only the preset pictures. The photo is cropped by the page's own `prepareImage` and uploaded (`POST /api/media?purpose=avatar`, then `PUT /api/me/profile`) the moment the account exists. | iOS, Android | Guideline 4.2: a reviewer should meet a system sheet in the first few seconds, not after signing up and finding a composer. The server takes a preset at sign-up and nothing else (`isAvatar()`), so the upload cannot happen until there is an account to own it — hence "picked first, attached a moment later". If it fails the account is still made and the preset is kept. `public/js/core/joinphoto.js`, injected by `native.js`; no page module changes, so no reference plate changes. | in force; tested against a fake Camera and a fake API (`mobile/test/bridge.test.mjs`), unverified on a device |
| D16 | Light taps buzz, a toast buzzes (success or error), the status bar tap scrolls to the top (iOS). | iOS, Android (scroll-to-top: iOS only) | Native feel. Android has no status-bar tap; there is no scroll-to-top gesture on Android yet. | in force on iOS, haptics on Android, no scroll-to-top on Android |
| D17 | Offline: the page is on the device, so the shell always loads; `GET /api/me` is remembered (name, counts, no token) for 14 days and used only if the network itself is down, so the chrome still shows who you are. Everything else shows the site's own error card. | iOS, Android | Checklist 16. | in force, unverified |
| D21 | **Members' photos are blobs, not URLs.** Signed in, every `/media/` image is fetched with the bearer token and shown as a `blob:` URL; signed out it is the plain URL. Costs: (1) **no browser HTTP-cache hit** for a photo (the Worker's `public, max-age=300` is not used; a photo seen on two pages is fetched twice, because blobs are revoked when the page is left); (2) **memory**: at most 40 blobs and 24 MB held at once, oldest dropped first, a photo shared by many images is held once, at most 4 requests in flight, so a page with more photos than that keeps the earlier ones as already-decoded images but cannot re-show them from their blob if the browser discards the decoded data; (3) a photo appears one request later than a plain `<img>` would start, behind a 1px transparent placeholder; (4) `img.src` reads as `blob:…`, not `/media/…`, and a photo that fails (404, not yours to see) is a broken image from a deliberately invalid data URL, never retried anonymously; (5) a link to a photo (`<a href="/media/…">`) opens in the system browser with no token, so only a public photo opens. | iOS, Android | A private photo cannot load in an `<img>` in the app: the Worker's CORP is `same-origin` for it and an image request carries no `Authorization` (contract §12). Uniform rather than fallback-on-error because an anonymous `<img>` load succeeds for photos that are public only to an anonymous viewer: a viewer who is blocked must not see them, and on the web the cookie makes the Worker decide per viewer. | in force; tested against a fake Worker (public, private, 404, blocked, cap, revoke), unverified on a device or against the real Worker |
